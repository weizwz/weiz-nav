# 图片与图标加载及缓存策略文档

本文档详细说明了本项目在不同环境（Web 端与浏览器插件端）下的图片加载控制、缓存机制以及针对第三方 API 限流（Rate Limiting）的应对方案。

## 1. Web 端缓存方案

Web 端的图片请求通过原生 `<img>` 标签发出，受限于同源策略，跨域图片通常以 `no-cors` 模式加载，产生 Opaque Response。其缓存由 Service Worker (`apps/web/public/sw.js`) 接管。

### 核心策略：纯强缓存 (Cache First)

- **匹配规则**：所有图片文件（`.png`, `.webp` 等）及特定的第三方图标服务（如 `favicon.im`, `api.iconify.design`）。
- **执行逻辑**：
  1. 拦截请求，检查 `IMAGE_CACHE` 缓存空间。
  2. 若命中缓存，立即返回结果，**绝不发起后台网络请求（抛弃 stale-while-revalidate）**，避免浪费并发请求配额。
  3. 若未命中缓存，则走网络获取。
- **跨域缓存处理**：明确允许缓存 `status === 0` (Opaque Response) 的响应。否则由于原生 `<img>` 标签的无跨域限制加载模式，第三方服务的图标将永远因 HTTP 状态校验失败而无法被存入 SW 缓存。

## 2. 插件版缓存方案

插件端在权限上拥有更大自由度，其请求可以无视普通跨域限制，缓存控制直接写在业务组件（`LinkCard.tsx`）中。

### 核心策略：Cache API 强干预

- **匹配规则**：仅在 `chrome.runtime.id` 存在时激活（`isExtension === true`）。
- **执行逻辑**：
  1. 不依赖 `<img>` 的默认加载，而是手动调用原生的 `caches.open('weiz-nav-icons-v1')` 匹配 `targetUrl`。
  2. 若命中缓存，将其转化为本地的 `blob:` URL 赋值给图片组件。
  3. 若未命中，通过 `fetch()` 获取资源，验证 `response.ok` (状态码 200)，将其克隆一份存入 `Cache API`，再转换为 `blob:` URL 渲染。
- **优势**：由于完全手动接管，资源一次成功拉取后即永久保存在本地缓存空间中，后续渲染零网络开销，完美避开并发限流。

## 3. 并发限流（Rate Limiting）应对方案

由于第三方服务（尤其是免费接口如 `favicon.im`）通常设有严苛的并发和频率限制。若短时间触发数十个请求，极易引发 429 (Too Many Requests) 或 403 报错，导致图标一片空白。为此需实施以下防抖压制策略。

### 策略 A：分类按需加载（取消 DOM 缓存）

- **问题现状**：旧版代码为追求极致切换速度，将所有分类的卡片预先渲染至 DOM 树，非活跃分类依靠 `display: none` 隐藏。这造成了极大的无效 DOM 节点堆积，且浏览器的懒加载在处理隐藏 DOM 时行为不可控，容易造成瞬时海量请求。
- **解决方案**：移除 CSS 隐藏机制，采用纯 React 条件渲染，仅当分类处于 `active` 状态时才予以渲染挂载。
- **效果**：将首屏 DOM 节点数量级和潜在的图标并发请求量，从全局总量缩减至单一分类量，削减 80% 以上的网络压力。

### 策略 B：图片并发调度器（Task Queue）

- **问题现状**：在单分类卡片数较多（如超过 20 张）且用户显示器较大时，首屏依然会同时暴露过多卡片，引发超频报错。
- **解决方案**：构建全局异步并发控制队列（建议并发上限设为 15 - 20）。
- **执行流程**：
  卡片组件挂载后，不再立即将 URL 赋值给 `<img>`。而是向全局调度器发起排队申请，当获取到令牌后才予以赋值。利用原生的 `onLoad` 和 `onError` 回调监听加载结束信号，并通知调度器释放令牌，处理下一个排队任务。
- **效果**：彻底从根本上抚平网络请求峰值，所有需走网络的图标均会以可控的瀑布流模式平滑加载。
